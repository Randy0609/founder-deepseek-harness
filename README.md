# 创业者-DeepSeek Harness

> founder-deepseek-harness · 公开起步版（2026-09-23）
> 面向中小企业经营者与创业者的跨行业任务管理与 DeepSeek Harness 插件项目。

**一句话定位：**以 DeepSeek Harness（DSH）为 Agent 运行底座，探索一套可按企业配置的**任务 ERP**：把经营问题变成有负责人、有来源、有状态、有验收回执的任务，再按需接入业务地图、动态上下文与角色 Agent。每家企业保留自己的业务系统、数据、权限与配置。本仓库目前只有设计和插件路线图，**尚无可安装插件或经过验证的企业部署**。

这里的“任务 ERP”是本项目的**产品方向**：管理跨系统的经营任务及其证据，不声称替代企业现有 ERP、CRM、财务、人事系统，也不表示当前已有可运行的任务管理系统。具体定义见[跨行业任务 ERP 设计](docs/TASK-ERP.md)。

本项目由 Randy0609 独立维护，与 DeepSeek 官方无隶属或背书关系，不分发官方运行时或使用官方标志作为项目图标。

## 1. DSH 是什么？先看官方项目

[DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)将 DSH 定义为一个开源的 **Agent Harness**：它基于 Cordis，把模型适配、工具、会话、Agent 循环和 Web 界面等能力组合成插件。用户通过 Profile 选择需要的插件与配置；插件可以在文档化的扩展位上增加或替换能力。[官方架构说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)解释了 Profile、Bundle 和插件加载关系。

官方 Web 版的入门命令是 npx @deepseek-ai/dsh web，详见[官方 README](https://github.com/deepseek-ai/deepseek-harness#run)。DSH 是 Agent 的运行和组合环境；它本身不是企业的 ERP、财务账本、数据仓库或 HR 系统。

**成熟度边界：**官方目前标为开发者预览版，明确提示可能有不兼容变更，并在[安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md)中指出尚未经过安全审计、不可视为生产就绪。以下经营场景是本项目的设计方向，不能据此认定 DSH 已适合直接承载真实企业生产数据。

## 2. 经营者为什么要研究 DSH？

当一个经营任务跨越项目资料、业务系统、团队规则和多个工具时，经营者需要知道：问题由谁负责、用了哪份事实、下一步是什么、结果由谁验收。DSH 的插件式组合为**按企业需求定制 Agent 工作环境**提供了技术起点；跨会话任务记录与业务事实接入仍需要本项目另行设计和验证。

| 经营者遇到的问题 | 这个项目准备解决的事 | 边界 |
|---|---|---|
| 每次开始都要重讲项目、目标和工作方式 | 工作台显示当前项目、任务与可信资料入口；任务可从已核实节点继续 | 上下文须有来源与版本；会话不能代替持久任务记录 |
| 订单、库存、客户、财务分别在不同系统 | 用受限适配器读取经过授权的指标或文档 | 原系统仍是事实来源；数据仓库建在 DSH 外部 |
| AI 给出了答案，却不知道用了哪份数据 | 在任务里附来源、口径、时间范围和待核实项 | 模型生成的结论需人工验收，不能代替财务或人事决定 |
| 每家公司流程不同 | 按需选择插件、Profile 和本机配置 | 通用插件公开；企业凭据、客户资料和专有规则留在企业环境 |

例如零售经营者问“哪些商品销量下降却仍占库存”，服务企业经营者问“哪些项目延期并影响回款”。两者的业务对象和指标不同，但都需要定义问题、读取获准的事实、形成建议、指定责任人并验收。这些是**合成场景中的设计例子**，不是已经跑通的客户案例。

**Maya-DSH 给出的设计参考**是工作台的信息组织：左侧任务与项目入口、中间会话输入区、右侧按需看文件。服装业务字段和专有流程不进入跨行业内核；本项目只抽象可复用的任务与界面需求，保留 DSH 原生输入与会话流程，不复制业务数据与专有代码。

## 3. 这个 GitHub 项目怎么做？

我们把“企业级经营中枢”作为**长期方向**，把“任务 ERP”作为待验证的产品定义，从一个可验收的经营任务开始。下表把服装经营场景中的构想抽象为跨行业能力，行业差异留给企业配置与行业包。

| 原场景中的概念 | 跨行业的公共能力 | 每家企业自行定义的部分 |
|---|---|---|
| 企业级决策中枢 | 任务、证据、建议、责任人和验收状态 | 决策权限、目标与经营口径 |
| 老板／财务／销售 Agent | 可配置的角色视角与任务模板 | 岗位职责、审批人、专有流程 |
| 企业地图（Business Ontology） | 业务对象及其关系、来源和版本的描述方式 | 商品、项目、合同、客户等具体对象和字段 |
| 企业 GPS（Dynamic Context） | 按任务组合有时间范围、口径和权限的当前资料 | 企业自己的数据源、刷新规则和指标定义 |
| 企业操作系统（Agent Harness） | DSH 的插件组合与 Agent 执行，加上本项目待开发的任务层 | 连接器、授权范围和外部动作规则 |

角色 Agent 是**同一任务上的不同职责与视角**，不是三套互不相通的业务数据。完整边界与任务字段见[任务 ERP 设计](docs/TASK-ERP.md)。

**GitHub 仓库本身不是 DSH 插件。**它将保存多个独立插件的源码、文档和可复现验证；只有未来在 packages/ 下实现、构建并装入 DSH Profile 的包，才会成为可运行的插件。[官方插件教程](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/index.md)展示了插件入口和挂载方式。

~~~text
企业现有业务系统与知识资料（事实与权限来源）
        ↓ 经过授权的受限接口、业务地图与动态上下文
任务记录（目标 / 负责人 / 状态 / 来源 / 待核实项）
        ↕ DSH Profile + 本仓库未来的可选插件与角色视角
证据与行动建议 → 负责人批准 → 外部执行回执 → 独立验收
~~~

第一项建议试点任务：**用合成数据完成一条跨会话的经营异常核查任务**。零售和服务两个合成样例共用一份任务契约，各自提供不同的对象与指标；输出来源、时间范围、缺口、建议和人工验收结果。这个任务是开发目标，仓库目前尚未实现。

| 模块方向 | 计划中的最小切片 | 当前状态 |
|---|---|---|
| 任务层 | 跨会话任务记录、状态、负责人和验收回执 | 契约与持久化接口待设计 |
| 工作台与角色 | 在 DSH 原生会话中查看任务；按职责切换视角 | `ui-workbench` 等计划中 |
| 企业地图 | 描述业务对象、关系、口径和来源 | 通用契约待设计；行业字段留在配置中 |
| 动态上下文 | 按任务读取有时间范围与权限的知识和指标 | 受限只读接入待验证 |
| 经营、财务、人事 | 行业与职能任务模板、建议草稿和人工验收 | 后续分场景受控试点 |

任务契约、行业边界与验收顺序见[任务 ERP 设计](docs/TASK-ERP.md)、[插件路线图](docs/PLUGIN-ROADMAP.md)和[架构边界](docs/ARCHITECTURE.md)。[Randy Context Hub](https://github.com/Randy0609/context-hub)关注更通用的上下文与规则组织；本仓库只维护 DSH 专用插件与集成方案。

## 4. 社区插件怎么选？

官方建议给插件仓库添加 [dsh-plugin 主题](https://github.com/topics/dsh-plugin)，但主题页是**发现入口，不是兼容性、安全性或经营适用性的认证**。我们先核对仓库是否真的声明 DSH 插件入口、许可证、目标版本、数据读写权限和可复现测试，再在隔离 Profile 试装。

第一批值得**研究和隔离试点**的社区项目：

| 方向 | 候选项目 | 为什么先看它 | 当前结论 |
|---|---|---|---|
| 上下文可见性 | [dsh-context](https://github.com/bowenliang123/dsh-context) | 展示会话上下文组成，适合检查 Agent 实际看到了什么 | 已核到插件声明；本仓库尚未试装 |
| 知识库 | [dsh-knowledge](https://github.com/lemoncat7/dsh-knowledge) | 提供本地知识库与检索，也有远程和写入能力 | 只用合成文档试点；先核权限与备份 |
| 财务流程 | [dsh-finance](https://github.com/zhang787jun/dsh-finance) | 提供对账、结账等工作流与校验工具 | 可研究流程设计；不能当作账务系统 |

数据库分析、商业策略和 HR 候选及版本差异见[社区插件评估](docs/COMMUNITY-PLUGINS.md)。**这些是源码与文档研究推荐，不是已在本项目验证的安装推荐。**
